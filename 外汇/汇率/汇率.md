## 汇率系统领域

汇率是跨境支付的核心数据，必须自建才能控成本、控风险、控体验。

- 统一多渠道汇率来源，避免不同银行、做市商汇率不一致；
- 控制汇率波动风险，做熔断、监控、异常拦截；汇率波动会直接造成公司亏损。自建系统才能做汇率波动阈值监控、自动熔断、自动刷新、异常汇率拦截。外部渠道不帮你控风险。
- 掌握自主定价权，通过加点形成客户汇率，这是公司重要盈利点；银行 / 渠道只给原始汇率，不能直接给用户用。必须自建系统，在原始汇率上加点（spread），形成商户汇率、用户汇率、渠道汇率这是支付公司最主要的盈利点之一
- 支持锁汇、挂单、套期保值等跨境必需的金融能力；
- 满足高并发、低延迟、高可用的支付要求，并支撑对账、业财、审计全链路。
- 对账、清算、业财一体化汇率是资金、账务、清算的基础数据。必须可追溯、可审计、可回放。外部汇率没有日志、没有回放能力，无法满足合规与业财要求。

#### 多源异构接入
   - 支持 Kafka、RocketMQ、RPC 上传、渠道推送、定时爬虫、手工报价等多种入口。
   - 不同来源的协议、字段、币种代码、精度、报价方向和交易时间不一致，需要分别适配。
       - src_user： 定义有哪些行情源：providerId、code、名称
       - src_channel_info 定义每个源支持哪些 rate_type、symbol、tenor，以及 factor、offset

   - 汇率主要存于  Redis + HBase方式
        - Redis中存储 FX:RATE:V3:{rateType}:{symbol}:{providerId}:{tenor} 的汇率，保存15天
        - HBase：历史行情， key键 R:{symbol}:{rateType}:{providerId}:{tenor}:{yyyyMMddHHmmss}

#### 合源

当一个货币对、同一个 rateType、同一个 tenor，有多个行情源时，按配置把这些源的价格合成一个复合价格。

它解决的是：

- 多个源价格不一致；
- 单源异常/过期；
- 想取平均、取优、取劣；
- 想给复合价格加固定点差。

| 策略 | 中文 | 逻辑 |
|---|---|---|
| DIRECT | 直接报价 | 直接取候选中的第一个源 |
| AVG | 求平均 | 对所有可用源求平均，剔除过期和 ERROR 源 |
| PP_BEST | PP 取优 | Bid 取最低，Ask 取最高 |
| PP_WORST | PP 取劣 | Bid 取最高，Ask 取最低 |
| USER_BEST | 用户取优 | 代码中等同 PP_WORST |
| USER_WORST | 用户取劣 | 代码中等同 PP_BEST |
| NORMAL_FIRST | 第一个状态正常 | 按配置顺序取第一个 NORMAL 源；没有则取最新 |
| FLOW_SIDE | 跟随另一边 | 一边已经选好源，另一边跟随同一个源/源集合 |

```
假设 EURUSD 有三个源：

| 源 | Bid | Ask |
|---|---:|---:|
| A | 1.1000 | 1.1003 |
| B | 1.0999 | 1.1002 |
| C | 1.1001 | 1.1004 |

### AVG

Bid = (1.1000 + 1.0999 + 1.1001) / 3 = 1.1000
Ask = (1.1003 + 1.1002 + 1.1004) / 3 = 1.1003

结果：

EURUSD = 1.1000 / 1.1003

### PP_BEST

Bid = min(1.1000, 1.0999, 1.1001) = 1.0999
Ask = max(1.1003, 1.1002, 1.1004) = 1.1004

结果：

EURUSD = 1.0999 / 1.1004

### PP_WORST

Bid = max(1.1000, 1.0999, 1.1001) = 1.1001
Ask = min(1.1003, 1.1002, 1.1004) = 1.1002

结果：

EURUSD = 1.1001 / 1.1002
```

    
#### 套算

本币就是“某个国家、地区或机构自己的货币”，也叫本地货币 / domestic currency。它是相对的，取决于“站在谁的角度”。

> 美元是全球外汇市场的“媒介货币/锚货币/公共计价单位”。因此，许多跨境公司会选用美元做为“本币”

```
以“美元”为本质为例子

直盘 = 带美元的盘；
   EUR/USD
   USD/JPY
交叉盘 = 不带美元的盘。
   EUR/GBP
   EUR/JPY
  
套算：说的是“价格怎么算出来”，即通过一个中间货币（通常是 USD）和两个已有汇率推导出目标汇率。 
1 EUR = 1.1000 USD
1 USD = 7.2000 CNY
所以：
1 EUR = 1.1000 × 7.2000 = 7.9200 CNY
```
##### 套算过程

- 步骤1：定义src_base_symbol —— 基础/直盘货币对
- 步骤2: 定义src_std_symbol 是“系统对外承认的标准货币”， 包括 支持/暂时不支持的
- 步骤3: 确定套算集合ALL ， {src_std_symbol 中支持 -  src_base_symbol - 白名单（行情源直推） } 
     1. 当有新的直盘汇率进来
     2. 算出要当前要套的集合T
        ```
        从 src_base_symbol 中取 SPOT 的 USD 货币对，例如：
           EURUSD   ← 本次进来的，排除
           GBPUSD
           USDCNY
           USDJPY
           USDHKD
           AUDUSD
           ...
        每个 USD 腿和 EURUSD 组合，都会推导出一个目标
           EURUSD + GBPUSD → EURGBP
           EURUSD + USDCNY → EURCNY
           EURUSD + USDJPY → EURJPY
   
         最后和 ALL 相交过滤得到T
        ```
 - 步骤4: src_channel_mix 是合源策略
       ```
           假设：

            
            
            src_channel_mix 中合源配置

            EURUSD:
              providerId  = 0        // 复合源
              bidSrcIds   = [A, B, C]
              askSrcIds   = [A, B, C]
              bidStrategy = AVG
              askStrategy = AVG

            USDCNY:
              providerId  = 0
              bidSrcIds   = [D, E]
              askSrcIds   = [D, E]
              bidStrategy = AVG
              askStrategy = AVG
            
            EURUSD 有 3 个源：A、B、C
            USDCNY 有 2 个源：D、E

            | A | 1.0998 | 1.1000 |
            | B | 1.1000 | 1.1002 |
            | C | 1.1002 | 1.1004 |
            | D | 7.1998 | 7.2002 |
            | E | 7.2000 | 7.2004 |

            EURUSD 复合 Bid = (1.0998 + 1.1000 + 1.1002) / 3 = 1.1000
            EURUSD 复合 Ask = (1.1000 + 1.1002 + 1.1004) / 3 = 1.1002
            USDCNY 复合 Bid = (7.1998 + 7.2000) / 2 = 7.1999
            USDCNY 复合 Ask = (7.2002 + 7.2004) / 2 = 7.2003
   
            可能得到复合 EURUSD：
            
            EURUSD = 7.1999 / 7.2003
        ```
- 步骤5: 高行情频率的并发策略
   ```
     线程池拒绝策略: 队列满时，丢弃最老的任务，保证新任务能进来。
   ```
#### 套算掉期

掉期点主要由利率差决定
> 掉期点 ≈ 即期汇率 × (报价货币利率 - 基准货币利率) × 期限 

   ```
     假设：
      USD 利率 = 5%
      CNY 利率 = 2%
      USD/CNY 即期 = 7.2000
      期限 = 30 天
      
      粗略计算：
      
      掉期点 ≈ 7.2000 × (2% - 5%) × 30 / 365
             ≈ -0.01775
   ```
以上是理论值，真实市场价格还会受：市场流动性/供需关系 决定。

- 远期汇率 ≈ 即期汇率 + 掉期点
- 掉期点 = 远期汇率 - 即期汇率

| 项目 | 远期 | 掉期 |
|---|---|---|
| 交易笔数 | 一笔 | 近端 + 远端两笔 |
| 价格 | 完整远期汇率 | 掉期点 |
| 资金交换 | 只有未来一次 | 近端和远端各一次 |
| 用途 | 锁定未来汇率 | 资金调拨、展期、融资 |

掉期的核心作用不是“赌汇率涨跌”，而是：

> 用一种货币换另一种货币一段时间，解决资金期限和币种错配问题。

可以把它理解成：以另一种货币为抵押的短期融资/资金调拨工具。

- 本外币资金调拨：企业或银行手里有人民币，但短期需要美元
- 外币融资：一家企业有美元资产，但需要人民币经营资金
- 远期展期：企业原来有一笔 1 个月远期，但到期时不想交割，想延到 3 个月



##### 套算交叉盘掉期

标准直盘的基础掉期点，当前系统主要是靠行情源推送；交叉盘掉期和反向货币对掉期是会在系统内计算的。

它和即期交叉盘不一样，通过任务方式触发，而非行情事件

1. 计算量比即期大很多
2. 掉期数据更新频率通常低于即期
3. 需要保证整条掉期曲线的一致性

以下是计算过程

- 步骤1: 行情源推送的直盘掉期点存在Redis中【缓存中有 直盘即期，直盘掉期】
   ```
     EURUSD
        SP Bid = 1.1000
        SP Ask = 1.1002
     1M 掉期点：
       Swap Bid = 20 pips
       Swap Ask = 24 pips

     USDCNY
       SP Bid = 7.2000
       SP Ask = 7.2005
     1M 掉期点：
      Swap Bid = 50 pips
      Swap Ask = 55 pips
   ```
- 步骤2: 计算直盘远期
  ```
     普通 tenor 的公式是： Forward = mid SP + Swap / factor

      EURUSD 1M 远期

      Bid = 1.1001 + 20 / 10000
          = 1.1001 + 0.0020
          = 1.1021
      
      Ask = 1.1001 + 24 / 10000
          = 1.1001 + 0.0024
          = 1.1025

      得到：
      
      EURUSD 1M Forward = 1.1021 / 1.1025

      USDCNY 1M 远期
      
      Bid = 7.20025 + 50 / 10000
          = 7.20025 + 0.0050
          = 7.20525
      
      Ask = 7.20025 + 55 / 10000
          = 7.20025 + 0.0055
          = 7.20575
      
      得到：
      
      USDCNY 1M Forward = 7.20525 / 7.20575
   ```
- 步骤3: 远期交叉
   ```
      目标：

      EURCNY = EURUSD × USDCNY
      
      所以：
      
      EURCNY 1M Forward Bid
        = 1.1021 × 7.20525
        = 7.940906
      
      EURCNY 1M Forward Ask
        = 1.1025 × 7.20575
        = 7.944339
      
      得到：
      
      EURCNY 1M Forward = 7.940906 / 7.944339
   ```
- 步骤4:即期交叉，直接取 Redis 里目标交叉盘自己的即期价格（如果前期已经套算过了）
     ```
      目标：

      EURCNY = EURUSD × USDCNY
      
      所以：
      
      EURCNY 1M Forward Bid
        = 1.1021 × 7.20525
        = 7.940906
      
      EURCNY 1M Forward Ask
        = 1.1025 × 7.20575
        = 7.944339
      
      得到：
      
      EURCNY 1M Forward = 7.940906 / 7.944339
    ```
 - 步骤 5：远期交叉减即期交叉    
    ```
      Swap Bid
        = 7.940906 - 7.920995
        = 0.019911
      
      Swap Ask
        = 7.944339 - 7.920995
        = 0.023344
      
      乘以 factor：
      
      Swap Bid = 0.019911 × 10000 ≈ 199.11 pips
      Swap Ask = 0.023344 × 10000 ≈ 233.44 pips
      
      最终：
      
      EURCNY 1M SWAP ≈ 199.11 / 233.44 pips
    ```

同理反向掉期过程如下

- 步骤1: 反向即期
    ```
      USDEUR SP Bid = 1 / 1.1002 ≈ 0.90892565
      USDEUR SP Ask = 1 / 1.1000 = 0.90909091
    ```
- 步骤2:反向 1M 远期    
    ```     
      USDEUR 1M Bid = 1 / 1.1025 ≈ 0.90702948
      USDEUR 1M Ask = 1 / 1.1021 ≈ 0.90735868
    ```
- 步骤3: 返回掉期
    ```     
      Swap Bid = 0.90702948 - 0.90892565
         = -0.00189617

      Swap Ask = 0.90735868 - 0.90909091
         = -0.00173223

      乘 反向 factor 后大约是：
      USDEUR 1M Swap ≈ -18.96 / -17.32 pips

      反向 factor是 100000000 / factor
    ```

用 1e8 / factor 后，反向 factor 仍然是比较整齐的 10 的幂：

| 正向 factor | 反向 factor |
|---:|---:|
| 10000 | 10000 |
| 100 | 1000000 |
| 1000000 | 100 |
| 1000 | 100000 |

这样反向价格能保留足够精度，尤其是：

USDJPY ≈ 100
JPYUSD ≈ 0.01

JPYUSD 需要更多小数位，所以反向 factor 会变得更大。

#### 汇率风控
它是分层风控：数据校验、实时规则、源状态/选源、多源合成保护、阈值风控、动作审计

##### 输入数据校验
这一层对所有来源都生效，但它只做基础合法性，不做价格偏离风控。

- bid/offer 是否为空；
- 即期价格是否小于等于 0；
- 时间是否比缓存中的旧；
- 货币对是否能映射到 src_std_symbol

### 报价引挚

负责把行情源、产品、用户、点差劣化、FTP 和快照组合成最终对客报价。

> 对客报价 = 行情源价格 + 劣化树匹配出的点差

以下是标签的询价因子
```
symbol    = EURUSD
rateType  = SPOT
tenor     = SP
derId     = 1001      // 租户
subId     = 10        // 子业务
userId    = 2001      // 用户
level     = 3
dealTime  = 2026-11-03 22:30  // 时间
quoteTime = T30S     // 锁价时长
treeType  = SPOT     // 用户选取劣化树
amount    = 500,000 USD
```

#### 劣化规则

根据各维度进行价格劣化

| 叶子节点 | 查询维度 | 用途与规则描述 | 额外因子 |
|---|---|---|---|
| USER | symbol + rateType + userId + tenor | 用户个性化点差：按用户命中配置后，将对应点差加入本次劣化结果 | 无 |
| LEVEL | symbol + rateType + derId + level + tenor | 用户等级点差：按业务线和等级命中后加入；请求未带等级时，需要用用户信息反查等级 | userId（用于反查等级） |
| SUB | derId + subId + symbol + rateType | 子业务差异化点差：按子业务命中后加入 | 无 |
| DER | symbol + derId + rateType + tenor | BU/业务线衍生价、基础点差：按业务线命中后加入 | 无 |
| NIGHT | derId + symbol + tenor + rateType | 低谷/节假日点差：询价时间处于低谷或节假日时，命中后加入，否则不加 | dealTime（询价业务时间） |
| PEAK | derId + symbol + tenor + rateType | 高峰点差：命中高峰配置后加入；标准高峰配置缺失会阻断本次报价 | 无 |
| QUOTE_TIME | symbol + timeType + derId | 锁价时长风险补偿点差：存在锁价时长时，命中后加入；必要配置缺失会阻断报价 | quoteTime（锁价时长） |
| DYNAMIC | userId/tag + symbol + rateType + tenor + subId + 时间窗口 | 指定时段内按权重随机调价或优化；命中后加入，并做防倒挂处理 | 当前时间/业务时间、用户标签 |
| FTP | symbol + tenor + rateType + derId | FTP 成本/收益点差：优先命中 FTP 配置后加入；未配置时按掉期或套算规则兜底 | 无 |
| ORDER_VOLUME | userId/global + symbol + 成交量档位 | 成交量阶梯点差：按累计成交量命中档位后加入；未命中不调整 | amount（本笔询价交易量） |
| DEFAULT | 无 | 0 BP 兜底：不查配置，直接加入 0 点差 | 无 |

当然还有控制节点

| 非叶子节点 | 子节点执行方式 | 适用场景 |
|---|---|---|
| SELECTOR | 按 sortOrder 排序，依次执行子节点；第一个返回 true 后停止 | 优先级、互斥选择，例如：USER 优先，未命中再走 LEVEL |
| SEQUENCE | 顺序执行所有子节点，不短路 | 多个劣化叠加，例如：用户 + 衍生价 + 夜间 + 高峰 |
| SUB_STRATEGY | 根据 subId 查询子业务策略，裁剪 USER_SELECTOR 或 SUB_SELECTOR，再执行剩余子节点 | 子业务差异化策略，例如：某子业务忽略用户劣化或忽略子业务劣化 |

将上述规则可以组装成一颗树（默认树）进行控制，也可以给某个部门、某个子业务、某个货币对单独配置一整棵劣化树，覆盖默认树。

```
   例如商户 derId=1001、子业务 subId=10、货币对 EURUSD，只走：
   
   个性化/等级 → 衍生价 → 高峰 → 成交量阶梯
   
   可以配置特殊子树：
   
   key = SPOT:1001:10:EURUSD
   
   树结构：
   
   M_ROOT [SEQUENCE]
   ├── USER_SELECTOR [SELECTOR]
   │   ├── USER [ACTION]
   │   └── LEVEL [ACTION]
   ├── DER [ACTION]
   ├── PEAK [ACTION]
   └── ORDER_VOLUME [ACTION]
   
   含义：
   
   M_ROOT
     ├─ 用户个性化 / 等级二选一
     ├─ BU 衍生价
     ├─ 高峰点差
     └─ 成交量阶梯点差
```
#### 锁汇

先把未来某笔换汇的价格锁定下来，客户在约定时间内按这个价格成交，不受期间市场价格波动影响。
```
询价请求
  → 指定 quoteTime（锁价时长）
  → 计算价格 + 点差 (依赖于劣化树的规则)
  → 生成 rateId
  → 写入 Redis 报价缓存 （过期时间为锁价时长）
  → 保存快照
  → 返回 rateId / buy / offer / timeout / validTill


调用方后续拿 rateId：

确认报价
  → 校验 rateId 是否还有效
  → 使用快照中的价格和劣化结果成交

```

#### 挂单

挂单主要有三种形式对应用户不同的需求

| 类型 | 新增时 | 触发方式 | 命中判断 | 场景 |
|---|---|---|---|---|
| SRC_ALERT | 直接按指定行情源价写 Redis 预池 | 行情源实时事件 | 用行情源事件价比较 | 用户需求：只关注某个指定行情源是否到价。 适合用户想看“某个源的价格到了提醒我”，不关心自己实际可成交价 |
| TRADE | 查用户价 → 反推行情源价 → 写 Redis 预池 | 行情源实时事件 | 重新查用户价比较 | 用户需求：设置一个目标价，到价后自动触发交易流程。 适合愿意按条件成交、不想自己盯盘的用户 |


##### 为什么有Redis 预池 
```
在SRC_ALERT场景中
如果没有预池，每条行情来了都要：

扫描数据库里所有活跃挂单
  → 逐个判断是否到价

成本太高。
有了预池：

行情来了
  → 只查 Redis 中对应的价格区间
  → 找到可能命中的 orderId
  → 再做用户价二次校验

Redis 预池结构:
ZSet（跳表）:
  score  = 反推后的行情源触发价
  member = orderId


在TRADE场景中
新增 TRADE 挂单时：

客户挂单价 7.2300
  → 查当前用户价和 RateSnapshot
  → 用当前 SpreadContext 反推
  → 得到行情源监听价 7.2264
  → 写入 Redis 预池

行情触发时：

行情源价格命中 7.2264
  → 重新查当前用户价
  → 用最新劣化树重新计算
  → 再和挂单价 7.2300 比较

```



### 汇率溯源

以下是当前系统的链路

```
第三方行情/Kafka
       │
       ▼
原始数据校验、标准化
OriginRateConvertProcess
       │
       ▼
BaseRateFromOriginEvent
       │
       ├───────────────┐
       │               │
       ▼               ▼
直盘清洗          交叉盘套算
RateAfterClean     CrossAlgorithm
       │               │
       └───────┬───────┘
               ▼
        保存单源行情
 内存缓存 + Redis + Kafka + Influx
               │
               ▼
           多源合源
       MixDomainServiceImpl
               │
               ▼
       BaseRate.traceObj （行情溯源信息对象）
               │
               ▼
           复合源行情
               │
               ▼
           (报价引挚)
               │
               ▼
     即期/掉期/远期/劣化计算
               │
               ▼
         Redis临时快照 (劣化信息) → 成交后Mongo
             
```

即通过  行情溯源信息对象 + 劣化信息 完成一个价格的溯源

```
USDRMB_FWD
├── id = rateId1
├── parent = [rateId1, rateId3]
├── span = A.B.C
│
├── USDRMB_SWAP
│   ├── id = rateId1
│   ├── parent = [rateId1, rateId2]
│   ├── span = A.B
│   │
│   ├── USD_RATE
│   │   ├── id = rateId1
│   │   ├── parent = []
│   │   └── span = A
│   │
│   └── RMB_RATE
│       ├── id = rateId2
│       ├── parent = []
│       └── span = B
│
└── USDRMB_SP
    ├── id = rateId3
    ├── parent = []
    └── span = C
```

USDRMB_FWD 由 USDRMB_SWAP 和 USDRMB_SP 计算得到。

直接父级：
parent = [rateId1, rateId3]

其中：
rateId1 对应 USDRMB_SWAP
rateId3 对应 USDRMB_SP

计算链经过：
基础汇率 A→ 掉期合成 B → 远期合成 C

所以：
span = A.B.C



HBase 结构的本质 这套设计可以概括为：
```
RowKey = 一条计算链的 rateId

Column = 该计算链经过的 span

Value = 当前 span 依赖的直接 parent rateId 数组
```

最长链路的层级数 = 就是 Hbase 的 列数。

| rateId | span=A | span=A.B | span=A.B.C |
|---|---|---|---|
| rateId1 | parent=[] | parent=[rateId1, rateId2] | parent=[rateId1, rateId3] |
| rateId2 |  | parent=[] |  |
| rateId3 |  |  | parent=[] |
